# Phase 1 — 较大改动

## 1.1 S-04 token 吊销

### 现状

- JWT 载荷：`sub`（用户名）+ `role` + `iat`/`exp`（12h），无 jti、无版本号。
- 改密（`AuthService.changePassword`）只更新密码哈希，**旧 token 改密后仍有效直到过期**；账号 `enabled=false` 同样不影响已签发 token。
- 过滤器（`JwtAuthenticationFilter`）只验签与过期，不查用户状态。

### 目标

- 改密后该用户**所有已签发 token 立即失效**（吊销粒度：按用户）。
- 为将来"停用用户"提供同一吊销通道（`enabled=false` 时旧 token 失效）。

### 方案设计（推荐：用户级 token_version）

| 项 | 设计 |
|---|---|
| **Schema**（V3 迁移，与 F13 合并一次迁移） | `ALTER TABLE sys_user ADD COLUMN token_version BIGINT NOT NULL DEFAULT 0;` |
| **签发** | `JwtService.generate` 增加 claim `ver` = 用户当前 `tokenVersion` |
| **校验** | `JwtAuthenticationFilter` 解析出 `ver` 后，与内存缓存中该用户的版本比对；不一致（或用户已停用）→ 不注入认证（走 401），并记 DEBUG 日志 |
| **吊销点** | `AuthService.changePassword`：`tokenVersion+1` 落库并更新内存缓存。停用用户（未来接口）同样 `+1` |
| **内存缓存** | 新组件 `UserAuthStateCache`：`ConcurrentHashMap<String, UserAuthState>`（含 `tokenVersion`、`enabled`）；启动 `@PostConstruct` 全量加载；变更点同步更新。**避免每请求阻塞查库**（不引入 DB 调用到事件循环） |
| **配置** | `gateway-dashboard.security.revoke-on-disable: true`（停用即吊销开关，默认开） |

### 为什么不选其他方案

- **jti 黑名单**：可精确到单个 token，但需要黑名单存储；内存版重启即失效，Redis 版引入基础设施依赖（本项目当前无 Redis）。
- **短 TTL + refresh token**：改动面大（登录协议、前端刷新链路），与 MVP 规模不匹配。

### 边界与取舍

- 内存缓存**单实例一致**；多实例场景需要缓存同步（与 1.3 的轮询/未来 Redis 联动，见 F5 演进路径）。
- 吊销粒度是"按用户全部 token"，不是单个会话；如需单会话吊销，需升级 jti 方案。

### 测试

- 改密前签发的 token 调用 `/api/routes` → 401；改密后新 token → 200。
- 未登录/坏 token 行为不回归（现有 `JwtServiceTest`、`GatewayDashboardIntegrationTest` 保持全绿）。

## 1.2 F13 校验和水印（单调 revision 水印）

### 现状

- `gateway-demo/RouteSyncScheduler` 每 5s 轮询 `SELECT CONCAT(COUNT(*), ':', COALESCE(SUM(version),0))` 判断变化。
- 理论碰撞：删除一行 + 新增一行（且版本和恰好抵消）时校验和不变 → 漏检。行数+版本和**不是单调的**。

### 目标

- 用**严格单调**的全局 revision 水印替换校验和，消除碰撞类漏检。
- 同一水印同时服务 1.3 的内嵌网关兜底与外部网关轮询（单一事实源）。

### 方案设计

| 项 | 设计 |
|---|---|
| **Schema**（V3 迁移） | `CREATE TABLE config_revision (id TINYINT PRIMARY KEY, revision BIGINT NOT NULL); INSERT INTO config_revision (id, revision) VALUES (1, 0);`（约定 id=1 单行） |
| **写入路径**（backend） | `RouteService` 的 create/update/delete/setEnabled **同一事务内**追加 `UPDATE config_revision SET revision = revision + 1 WHERE id = 1`（原子自增，行锁串行化写）；`SeedDataInitializer` 种子写入同样 bump |
| **统一写路径约束** | 所有"真源写入"必须经 `RouteService`（或显式 bump 的入口）；README/使用手册声明"绕过写路径的直连 SQL 不会被轮询感知" |
| **读取路径**（gateway-demo） | `RouteSyncScheduler.currentChecksum()` → `SELECT revision FROM config_revision WHERE id = 1`；`lastChecksum/lastRefreshedChecksum` 语义不变（仍是 `synchronized` + markRefreshed 模式，值从校验和换为 revision） |
| **并发** | `UPDATE ... SET revision = revision + 1` 是原子语句，无需应用层锁；gateway-demo 侧沿用现有 synchronized 防竞态 |

### 为什么是独立水印表而不是复用 `route_config.version`

- `@Version` 是**行级**版本号，只对单行更新单调；跨行（新增/删除）没有全局次序。
- 独立单行表提供**全局单调序列**，且不侵入业务表语义。

### 测试

- 新增/删除/更新路由后 revision 严格 +1（集成断言，多步写后读 revision）。
- gateway-demo `RouteSyncSchedulerTest` 改为 mock revision 列：变化触发一次刷新、markRefreshed 抑制、再次变化兜底触发（沿用现有用例结构）。

## 1.3 F5 多实例兜底（内嵌网关轮询兜底）

### 现状

- **内嵌网关**只在本地写路径触发刷新（`RouteService.afterCommit` → `RefreshRoutesEvent`）；若另一实例（或直连 DB）改了路由，本实例**无兜底**。
- **外部网关**（gateway-demo）已有 5s 轮询兜底（校验和方案，1.2 中升级为 revision）。

### 目标

- 内嵌网关获得与外部网关同等的兜底：外部变更 ≤ 一个轮询周期（默认 5s）生效，**无需引入新基础设施**。

### 方案设计

| 项 | 设计 |
|---|---|
| **新组件** | `EmbeddedGatewaySyncScheduler`（backend）：`@Scheduled(fixedDelayString = "${gateway-dashboard.route-sync.poll-interval-ms:5000}")` |
| **轮询逻辑** | 读 `config_revision`；`revision != lastSeenRevision && revision != lastRefreshedRevision` → 发布 `RefreshRoutesEvent` + 记录 `lastRefreshedRevision`（与 gateway-demo 完全同构） |
| **本地写联动** | `RouteService` 刷新后同步 `lastRefreshedRevision = 当前 revision`（把现有 `scheduleRefreshAfterCommit` 与调度器状态打通），避免本地写 → 轮询重复刷新 |
| **配置** | `gateway-dashboard.route-sync.enabled`（默认 true，可关）+ `poll-interval-ms`（默认 5000） |
| **幂等性** | 刷新 = 读库重建路由定义，重复刷新无害；`lastRefreshed` 判断只为避免同一次变更重复刷新的日志噪音 |
| **演进路径**（不实现，仅记录） | 需要低延迟传播时引入 Redis pub/sub 替代/补充轮询；届时 `UserAuthStateCache`（1.1）也可借同一通道做多实例缓存失效 |

### 为什么不选 Redis pub/sub 作为主方案

- 项目当前无 Redis 依赖、单实例 MVP；轮询与 gateway-demo 既有机制同构，零新依赖。延迟敏感场景再演进。

### 测试

- 模拟"他实例写入"：绕过本地刷新路径直接改 revision（或改 DB 行）→ ≤ 轮询周期后 `/api/gateway/status` 生效路由更新。
- 本地写不重复刷新：写路由后 revision 变化一次，刷新恰好一次（日志/状态时间戳断言）。
- 配置 `enabled=false` 时调度器不运行。

# Phase 2 — 低优先级

## 2.1 404 统一 JSON

### 现状

- 未匹配路径由 WebFlux 默认 `DefaultErrorWebExceptionHandler` 输出默认错误 JSON（含 timestamp/error/path），**不是**统一 `ApiResponse` 信封（README 声称"统一响应体"）。

### 方案

- 新增 `WebExceptionHandler` bean，`@Order(-2)`（早于默认错误处理器 order -1），**仅**处理 404（`ResponseStatusException(NOT_FOUND)` 或响应状态 404），输出 `ApiResponse.fail(404, "接口不存在")`；其余异常放行默认链。
- 不动 SecurityConfig 已有的 401/403 处理（已统一信封）。

### 风险与验证

- 必须回归：网关**代理转发**路径不受影响（处理器只接 404，不接匹配路由的转发响应）；OPTIONS 预检不被误伤。
- 集成测试：`GET /api/no-such-endpoint` → 404 + `{code:404}`；`GET /actuator/health` 等仍正常。

## 2.2 登录限流

### 现状

- `/api/auth/login` 无任何限流，可被暴力破解（默认口令 + BCrypt 成本 = 攻击面）。

### 方案（已确认：Bucket4j 令牌桶）

| 项 | 设计 |
|---|---|
| **依赖** | `com.bucket4j:bucket4j-core`（8.x，Java 21 兼容）。**环境约束**：该依赖不在本地 Maven 仓库，实施时需要联网下载，沙箱默认阻止写入 `~/.m2`，需用户批准一次更宽的沙箱权限（或临时换用无依赖方案） |
| **桶结构** | 每 IP 一个令牌桶：容量 `capacity`（默认 10）+ 匀速补充 `refill`（默认 10 个/分钟），`Bucket4j.builder().addLimit(Bandwidth.classic(capacity, Refill.greedy(refill, Duration.ofMinutes(1))))` |
| **阈值** | `gateway-dashboard.security.login-rate-limit.capacity` / `.refill-per-minute`（可配） |
| **行为** | 每次登录尝试先 `tryConsume(1)`；桶空 → 抛 `BusinessException`（新增 `TOO_MANY_REQUESTS` 工厂，429）+ 统一 JSON；**登录成功** → 重置该 IP 桶（避免误伤正常用户） |
| **桶存储** | `ConcurrentHashMap<ip, Bucket>`，配合定期清理空闲桶（或 Guava Cache 式过期，避免内存泄漏） |
| **挂载点** | `AuthService.login` 入口（阻塞侧，令牌桶为纯内存操作，无 IO） |
| **IP 口径** | 与审计 IP 一致（`SecurityUtils.clientIp`，信任 X-Forwarded-For 的边界沿用文档声明；受信代理场景建议改 X-Real-IP） |

### 取舍

- 桶存储为**单实例内存**：多实例各自计数（MVP 可接受，与 1.3 演进同步）；重启清零。
- 令牌桶比固定窗口平滑（突发允许短暂超过平均速率），符合"登录限流"典型用法。

### 测试

- 连续失败 N+1 次 → 429；第 N+1 次后窗口外恢复（用可注入时钟或小窗口配置）。
- 登录成功后计数清零不误伤。

## 2.3 密码最短 8 位

### 现状

- 后端 `AuthDtos.java:15` `@Size(min=6)`；前端 `App.vue:33` `length < 6`。

### 方案

- 后端 `@Size(min=8)` + 前端同步 `< 8`；`README`/`使用手册` 同步。
- 存量账号不受影响（admin123=8、viewer123=9 均满足）；仅约束**新设/修改**密码。
- 复杂度（大小写+数字）作为可选项写入文档，不强制（避免改密兼容性负担）。

### 测试

- 7 位新密码 → 400；8 位 → 200；改密后旧 token 失效（联动 1.1 断言）。

## 2.5 覆盖率门槛

# 风险与取舍汇总

| 项 | 取舍/风险 | 缓解 |
|---|---|---|
| S-04 内存缓存 | 单实例一致；多实例需缓存同步 | 与 F5 演进路径（Redis）联动；文档标注边界 |
| F13 水印 | 绕过 RouteService 的直连 SQL 写不会被感知 | 统一写路径约束写入文档；审计已记录变更来源 |
| F5 轮询 | 5s 延迟窗口（可配）；多实例各自轮询 | 刷新幂等无害；延迟敏感再上 pub/sub |
| 404 处理器 | 可能误伤网关转发/OPTIONS | 仅接 404 + 回归测试 |
| 限流内存窗口 | 重启清零、多实例各自计数 | MVP 可接受；文档标注 |
| Bucket4j 依赖 | 本地仓库无该依赖，沙箱默认阻止写 `~/.m2` | 实施时申请一次更宽的沙箱权限完成下载；若不可行回退无依赖固定窗口 |
| 覆盖率门槛 | 一次性提高会卡构建 | 先实测后设低门槛，逐步收紧 |

# 验收标准

- Phase 1：改密后旧 token 立即 401；revision 随每次写严格 +1；他实例写入 ≤ 轮询周期在内嵌网关生效；backend + gateway-demo 新旧测试全绿。
- Phase 2：未知路径 404 返回统一信封；登录连续失败触发 429；新密码 < 8 位被拒（前后端一致）；前端组件测试引入；`mvn verify` / `npm test -- --coverage` 输出覆盖率且过门槛。
- 全部完成后更新 `docs/优化报告.md` 的剩余 backlog 与 `README`。
