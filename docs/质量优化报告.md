## 2. 本轮修复

### O1（Correctness，Required）— 单行坏数据冻结全部路由（真实缺陷）

- **问题**：`RouteAssembler.readSteps/readMetadata` 对非法 JSON 抛 `IllegalStateException`；`DbRouteDefinitionLocator`（backend 与 gateway-demo）逐行 `map(toDefinition)`，**任何一行损坏 → 整个 Flux 失败** → 生效路由刷新失败、状态页 500、流量路由停滞，且失败被预热 catch 静默吞掉（仅 WARN）。
- **修复**：`onErrorContinue` 跳过损坏行并 `log.error`（含 routeId 与原因），其余路由照常生效。管理端列表/详情接口**保持失败出声**（管理员需要看到坏行才能定位修复）——两侧语义刻意不同，已注释说明。
- **回归测试**：`DbRouteDefinitionLocatorTest` —— 直插一条非法 `predicates_json` 路由，断言 Flux 正常完成且只加载合法路由；日志确认 ERROR 输出。

### O2（Readability，Required）— 统一 JSON 错误写出近重复

- **问题**：`SecurityConfig.writeJson`（401/403）与 `UnifiedNotFoundWebExceptionHandler`（404）各自用 ObjectMapper 写同一信封，逻辑重复。
- **修复**：新增 `common/HttpJsonWriter.writeError(...)` 作为唯一实现，两处改为委托。

### O3（Architecture/Correctness，Required）— 权限缓存提交前更新

- **问题**：`PermissionRuleService.create/update/delete` 在事务内直接 `reload()` 更新内存缓存；若事务随后回滚（如 save 失败），缓存与库不一致。且与 RouteService/Seed 的 afterCommit 模式不一致。
- **修复**：新增 `reloadAfterCommit()`（`TransactionSynchronization.afterCommit` 触发 reload；无事务时直接 reload），与既有模式统一。动态权限"修改即生效"语义不变（afterCommit 在响应返回前同步执行）。

### O4（Dead Code Hygiene，用户确认后删除）

按技能"死代码卫生"要求列出并征得用户同意后删除（git 历史可追溯）：
- `api/routes.ts` → `routesApi.get(routeId)`（无调用点）
- `stores/auth.ts` → `fetchMe()` 动作
- `api/auth.ts` → `authApi.me()`（仅被 fetchMe 引用）
- 同步清理：`auth.test.ts` 中对应 mock 项、`api/auth.ts` 的 `get`/`UserSummary` 引用

## 3. 复核通过项（诚实记录：已查、无需改动）

- **正确性**：afterCommit 事件链（刷新→标记→推送）顺序与回滚语义；乐观锁 409；`setEnabled` 同状态短路；限流"成功重置"；S-04 吊销缓存一致性；种子事件提交后发布——均已复核无新问题。
- **可读性**：命名/注释与项目约定一致；无嵌套三元、无深层回调；`EmbeddedGatewaySyncScheduler` 的 lastSeen/lastRefreshed 双标记注释清晰。
- **架构**：`refresh` 包独立后依赖为 DAG；`RouteChangeSyncListener` 编排职责单一；无 over-engineering（未引入多余抽象）。
- **安全**：本轮零新攻击面；SQL 全参数化；无密钥入库；日志无敏感数据。
- **性能**：`EmbeddedGatewaySyncScheduler` 每 5s 一次主键查询可忽略；审计分页 size 上限 100；无大对象热路径。
